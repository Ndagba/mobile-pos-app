# MobilePOS — Production Deployment Runbook (Nov 2026)

**Server:** Opalstack · app root `/home/pcnexamdistro/apps/pcnexamdistro/myproject/`
**Deploy method:** FileZilla (SFTP) upload of compiled output + PuTTY (SSH) for DB/migration/restart
**Database:** Opalstack PostgreSQL (`pg_dump` available on the shell)
**Public API:** `https://distro.pcnigeria.org.ng/v1` (health at `/health`)
**Baseline:** the **August 2026** deploy is live (migration `20260819…item_type/Decimal` applied → 5 migrations tracked).

> Do this during a low-traffic window and warn clients of a **~2–3 minute** planned pause.
> You have existing clients on the live system. If any command output looks unexpected, **STOP** and review before continuing.
> This deploy is **backward-compatible** — the currently-installed mobile app keeps working unchanged throughout.

---

## What this deploy contains

| Item | Risk | Mitigation |
|---|---|---|
| **3 new migrations — all strictly additive** (`CREATE TABLE` / nullable `ADD COLUMN` / index / FK only) | **None** — no table rewrite, no `DROP`/rename/type-change | New tables start empty; new columns are nullable/defaulted; existing rows untouched |
| New route/service code (`/v1/locations`, `/v1/expenses`, `/v1/financials`, `/v1/reports`, `/v1/purchase-orders`) | Serves old data fine | Uploaded over old `dist/`; old copy kept for instant rollback |
| Dependencies | — | Only `@radix-ui/react-switch` added since August — a **frontend** package the backend never imports → **no `npm install`** |
| Environment variables | — | **None added** — no `.env` change |

**Pending migrations (exactly 3), in order:**
1. `20260907140000_add_purchase_orders` — 4 new tables (PurchaseOrder/Item, GoodsReceipt/Item) + nullable `PurchaseInvoice.purchase_order_id` + indexes/FKs
2. `20261029133319_add_locations_and_payment_splits` — `Location` table + nullable `Product.location_id` + nullable `Transaction.payment_splits` (JSONB) + indexes/FKs
3. `20261102000000_add_store_settings_fields` — 9 nullable/defaulted columns on `StoreSetting`

All three contain **only** `CREATE TABLE`, `ADD COLUMN`, `CREATE INDEX`, `ADD CONSTRAINT … FOREIGN KEY`. **No `DROP`, `DELETE`, rename, or table recreation**, and no `USING ::` type casts. Nothing rewrites an existing table.

**Three hard gates:** (1) full DB backup before migrating · (2) confirm the live migration history is in sync — **5 applied, these 3 pending, none failed/modified** — *before* applying · (3) regenerate the Prisma client on the server after.

## Step 2 — Server prep + read-only diagnosis (PuTTY, app still running — no downtime)

```bash
cd /home/pcnexamdistro/apps/pcnexamdistro/myproject
# tr -d '\r' strips Windows CRLF; sed strips surrounding quotes.
export DATABASE_URL="$(grep -E '^DATABASE_URL=' .env | head -1 | cut -d= -f2- | tr -d '\r' | sed 's/^"//; s/"$//')"
echo "$DATABASE_URL" | sed -E 's#(://[^:]+:)[^@]+@#\1****@#'   # verify: ends at db name, no trailing " or %22
psql "$DATABASE_URL" -c "SELECT 1;"                            # connectivity sanity check
```

Back up the current **code** (instant rollback; originals stay in place):

```bash
cp -r dist "dist_backup_$(date +%F_%H%M)"
cp prisma/schema.prisma "prisma/schema.prisma.bak_$(date +%F_%H%M)"
ls -d dist_backup_* && echo "code backup OK"
```

**Read-only diagnosis — all SQL below only reads. This confirms we are on the expected baseline and nothing is half-applied.**

```bash
# (a) Migration history — expect the 5 August-era migrations, all finished, and NONE of the 3 new ones.
psql "$DATABASE_URL" -c 'SELECT migration_name, finished_at, rolled_back_at FROM "_prisma_migrations" ORDER BY started_at;'

# (b) Proof the August deploy is in (its effects present).
psql "$DATABASE_URL" -c "SELECT column_name FROM information_schema.columns WHERE table_name='Product' AND column_name='item_type';"
psql "$DATABASE_URL" -c "SELECT data_type FROM information_schema.columns WHERE table_name='Inventory' AND column_name='quantity_on_hand';"

# (c) Prerequisite tables the 3 new migrations reference must already exist.
psql "$DATABASE_URL" -c "SELECT table_name FROM information_schema.tables WHERE table_schema='public' AND table_name IN ('Supplier','PurchaseInvoice','StoreSetting','Branch','Product','Transaction') ORDER BY table_name;"

# (d) The 3 new tables must NOT exist yet (0 rows returned).
psql "$DATABASE_URL" -c "SELECT table_name FROM information_schema.tables WHERE table_schema='public' AND table_name IN ('PurchaseOrder','Location','GoodsReceipt');"

# (e) Prisma CLI available on the server.
node_modules/.bin/prisma -v || echo ">>> PRISMA CLI MISSING"
```

| (a) history | (b) item_type / qty type | (c) prereq tables | (d) new tables | Decision |
|---|---|---|---|---|
| 5 migrations finished, ending at `20260819…`; **none** of the 3 new present | `item_type` present · `numeric` | all 6 listed | 0 rows | **GO** — proceed to Step 3, then deploy the 3 |
| `20260819…` **absent**, or `item_type` absent, or qty `bigint`/`integer` | — | — | — | **STOP** — August never landed; this is a different/heavier window (use the August runbook first) |
| any of `PurchaseOrder`/`Location`/`GoodsReceipt` already exists, **or** a new migration already in history | — | — | ≥1 row | **STOP** — partially applied; investigate before touching anything |
| any prereq table (c) missing | — | missing | — | **STOP** — schema is behind expectation; investigate |
| `PRISMA CLI MISSING` | — | — | — | `npm install prisma@^5.7.0 --no-save`, then re-check |

## Step 3 — Upload new code (FileZilla)

Upload `backend\dist\` and `backend\prisma\` over the server copies under `.../myproject/`.
Overwriting while the app runs is safe — the live process holds old code in memory. **Nothing is live yet.**

> Upload the **entire** `prisma\` folder, including `prisma\migrations\` with **all 8** migration subfolders. The 5 existing ones must be byte-identical to what's already tracked (they are — unchanged in git), or `migrate deploy` will refuse with a "modified" error.

**After the upload — still read-only, app still up — final gate before the window:**

```bash
ls prisma/migrations/20260907140000_add_purchase_orders/migration.sql
ls prisma/migrations/20261029133319_add_locations_and_payment_splits/migration.sql
ls prisma/migrations/20261102000000_add_store_settings_fields/migration.sql
node_modules/.bin/prisma migrate status --schema prisma/schema.prisma
```

> **Pass `--schema prisma/schema.prisma`.** If the server still has the stale legacy root `schema.prisma` (it was optionally retired in August's Step 5b), a *bare* command may read the wrong one. Passing `--schema` is always safe.

`migrate status` must report **exactly 3 migrations not yet applied** — the 3 listed above — with the 5 older ones applied, **no failed migration, and no "modified" warning**. That is the green light for Step 4. Anything else → **STOP**.

## Step 4 — Maintenance window (PuTTY)

> Every Prisma command uses `--schema prisma/schema.prisma`. The `$DATABASE_URL` export is repeated in case this is a fresh PuTTY session. Only **sub-step 3** writes to the database — and only after the backup in sub-step 2.

**1) Set env + stop the app:**

```bash
cd /home/pcnexamdistro/apps/pcnexamdistro/myproject
export DATABASE_URL="$(grep -E '^DATABASE_URL=' .env | head -1 | cut -d= -f2- | tr -d '\r' | sed 's/^"//; s/"$//')"
psql "$DATABASE_URL" -c "SELECT 1;"          # env sanity — must return 1
~/apps/pcnexamdistro/stop                    # expect: "Stopped pcnexamdistro."
```

**2) Authoritative DB backup (nothing writes once the app is stopped) + baseline row counts:**

```bash
pg_dump "$DATABASE_URL" -Fc -f ~/pos_backup_$(date +%Y%m%d_%H%M%S).dump
ls -lh ~/pos_backup_*.dump    # confirm non-zero size — DO NOT proceed if this failed
psql "$DATABASE_URL" -c "SELECT (SELECT count(*) FROM \"Product\") AS products, (SELECT count(*) FROM \"Transaction\") AS transactions, (SELECT count(*) FROM \"TransactionItem\") AS tx_items, (SELECT count(*) FROM \"Inventory\") AS inventory;"
```

**Write down those 4 counts** — Step 5 must match them exactly (additive migrations add tables/columns; they never change existing row counts).

**3) Apply the migrations:**

```bash
node_modules/.bin/prisma migrate deploy --schema prisma/schema.prisma
```

Expected: **3 migrations applied** — `20260907140000_add_purchase_orders`, `20261029133319_add_locations_and_payment_splits`, `20261102000000_add_store_settings_fields` — and nothing else.

> **If deploy errors with P3009 "failed migrations"** (not expected on a clean baseline): a row has *both* `finished_at` and `rolled_back_at` empty. Mark it rolled back with Prisma's own tool, then retry:
> ```bash
> psql "$DATABASE_URL" -c "SELECT migration_name FROM \"_prisma_migrations\" WHERE finished_at IS NULL AND rolled_back_at IS NULL;"
> node_modules/.bin/prisma migrate resolve --rolled-back <name_from_above> --schema prisma/schema.prisma
> node_modules/.bin/prisma migrate deploy --schema prisma/schema.prisma
> ```

**4) Regenerate the client (server-native engine), then force a clean restart:**

```bash
node_modules/.bin/prisma generate --schema prisma/schema.prisma
~/apps/pcnexamdistro/stop                    # kill the process that predates the regen
sleep 2
~/apps/pcnexamdistro/start                   # expect: "Started pcnexamdistro."
```

> ⚠️ **Opalstack keepalive cron** re-runs `start` every few minutes, so the app may auto-resurrect while stopped (a bare `start` then prints *"already running"*). A process that started *before* `prisma generate` holds the **old** client in memory and won't know the new tables/columns even though `/health` is green — so after generating you **must** `stop` → `start`. Confirm the log shows a **fresh** `Server running on port …` timestamp *after* the regen.

## Step 6 — Rollback (only if a check fails)

Pre-deploy state = the August baseline (schema **without** the 3 new models).

```bash
~/apps/pcnexamdistro/stop
# 1) Restore the database from Step 4's dump.
pg_restore --clean --if-exists --no-owner -d "$DATABASE_URL" ~/pos_backup_YYYYMMDD_HHMMSS.dump
# 2) Restore the old compiled code.
rm -rf dist && cp -r dist_backup_YYYY-MM-DD_HHMM dist
# 3) Restore the pre-upload schema so the client matches the restored DB + old dist.
cp prisma/schema.prisma.bak_YYYY-MM-DD_HHMM prisma/schema.prisma
node_modules/.bin/prisma generate --schema prisma/schema.prisma
~/apps/pcnexamdistro/start
```

Returns database **and** code to the exact pre-deploy state. (Substitute the real backup filenames from Steps 2 and 4.)

## Step 7 — Ship the updated mobile app (APK)

The backend is backward-compatible, so the **currently-installed** app keeps working. The new shelf-location and expenses features appear only after clients install a new APK.

> ⚠️ **Build the client APK against production.** `mobile/eas.json` sets `EXPO_PUBLIC_API_URL=https://distro.pcnigeria.org.ng/v1`, so an **EAS build** (`eas build -p android`) targets the live server. A local `gradlew assembleRelease` build may embed `mobile/.env`'s LAN IP instead — fine for your own test device, **not** for clients. For client distribution, build with EAS (or confirm the production URL is baked in) before handing the `.apk` out.

- Distribute the `.apk` to clients; they install over the existing app.
- Data survives the update **if the APK is signed with the same key** as the installed app. A different key forces an uninstall (clears only local cache/login — all real data is on the server) and a re-login.
- Bump `version` / `versionCode` in `mobile/app.json` for each new APK.

## Quick reference — order of operations

1. PC: `cd backend && npm run build` → have fresh `dist/` + `prisma/` ready
2. PuTTY: set `DATABASE_URL`, back up code, **run read-only diagnosis** → confirm GO (5 applied, 3 pending)
3. FileZilla: upload `dist/` + `prisma/` (all 8 migration folders) → `migrate status --schema prisma/schema.prisma` shows exactly 3 pending
4. PuTTY window: `stop` → `pg_dump` + counts → `migrate deploy` (3 applied) → `prisma generate` → `stop` → `start`
5. Verify: health + identical counts + 3 new tables + new routes return 401 + test sale
6. Rollback only if a check fails
7. Distribute a **production-targeted** APK to clients
